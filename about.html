The problem I keep getting hired to fix.

Design and code drift apart. The Figma file says one thing, the codebase says another, and after a year nobody trusts either.

Most teams I join already have a system. Design describes it one way and engineering describes it another.

Bullhorn is the clearest example.

Bullhorn had no Figma library. The code was the only record of what anything was supposed to look like. I proposed a token system, got engineering on board, and built more than 500 components on top of it.

Five developers now build from it instead of working it out.

How I work.

I help a team settle what it disagrees about. Then I build the answer into the system, so nobody has to settle it again.

Four rules I try not to break.

Build systems that hold up

At Bullhorn, 889 of 903 component tokens point at a name instead of a value.

Build accessibility in from the first draft

In software, every color pair is checked in five brand and theme combinations on every pull request. A contrast failure fails the build.

Let the constraints shape the work

Union Home Mortgage had backend engineers and no designer in the room, so I built components they could implement without one.

Say what isn't finished

Fourteen Bullhorn tokens still hold raw values. The case study says so, because I'd rather name a gap than have someone find it.
